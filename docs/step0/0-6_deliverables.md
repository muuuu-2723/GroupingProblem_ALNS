# 成果物一覧の定義

## 1. 目的

本項目では、「卒論プログラムリファクタリング」プロジェクトで作成する成果物を定義する。

本プロジェクトは個人プロジェクトであるため、過度に厳格な成果物管理は行わない。  
一方で、以下の理由から、必要な成果物は明文化してGit管理する。

- STEP間の作業インプットを明確にするため
- GitHub Copilot Agent Modeに作業を依頼しやすくするため
- 後から判断理由や設計意図を確認できるようにするため
- 複雑な探索アルゴリズムの理解を補助するため
- リファクタリング後の妥当性確認に使うため

---

## 2. 成果物分類の考え方

成果物は以下の3区分で管理する。

| 区分 | 意味 |
|---|---|
| 必須 | 作成しないと次工程に進みにくいもの、または完了判断に必要なもの |
| 準必須 | 簡易版でよいが、後続作業やレビューのために残した方がよいもの |
| 任意 | 必要になった場合のみ作成するもの |

---

## 3. 成果物の判断基準

成果物を必須・準必須・任意に分類する際は、以下の基準で判断する。

| 判断基準 | 扱い |
|---|---|
| 次工程のインプットになる | 必須 |
| 完了判断に使う | 必須 |
| Copilotへの作業指示に使う | 必須 |
| 判断理由を後から確認したい | 準必須以上 |
| 複雑な処理理解に必要 | 必須または準必須 |
| 作成コストが高く、使う場面が限定的 | 任意 |
| 作っても用途が明確でない | 作成しない |

## 5. STEP.0 成果物

STEP.0では、プロジェクト準備、環境整備、方針決定に関する成果物を作成する。

### 5-1. STEP.0 成果物一覧

| ファイル名 | 日本語名 | 区分 | 記載概要 |
|---|---|---|---|
| `0-1_project_goal.md` | プロジェクト目的・ゴール定義 | 必須 | プロジェクトの目的、最終ゴール、重視する観点、完了条件を記載する。 |
| `0-2_program_overview.md` | 対象プログラム概要 | 必須 | 現行プログラムの概要、対象問題、使用技術、入出力、探索アルゴリズム、対象範囲を記載する。 |
| `0-3_source_preservation.md` | 現行プログラム保全 | 必須 | Git管理方針、リファクタリング前タグ、ブランチ運用、不要ファイル整理、`.gitignore` 方針を記載する。 |
| `0-4_copilot_environment.md` | GitHub Copilot利用環境 | 必須 | VS CodeでのCopilot利用環境、Agent Mode使用方針、プロンプト管理、レビュー指摘票運用を記載する。 |
| `0-5_development_environment.md` | 開発環境・実行環境 | 必須 | ビルド手順、実行手順、コンパイラ、OpenMP、文字コード、デバッグモード、動作確認基準を記載する。 |
| `0-6_deliverables.md` | 成果物一覧定義 | 必須 | プロジェクト全体で作成する成果物、必須・準必須・任意の分類、各ファイルの役割を記載する。 |
| `0-7_working_rules.md` | 作業ルール定義 | 必須 | Git運用、コミットルール、Copilot利用ルール、レビュー方法、作業単位、確認手順を記載する。 |
| `0-8_refactoring_policy.md` | リファクタリング方針 | 必須 | 既存機能維持、コメント整備、JSON入力見直し、焼きなまし法追加、変更許容範囲を記載する。 |
| `0-10_step1_start_checklist.md` | STEP.1開始チェックリスト | 準必須 | STEP.0完了条件と、STEP.1へ進む前に確認する項目をチェックリスト形式で記載する。 |

### 5-2. STEP.0 成果物の補足

STEP.0の成果物は、以降の作業の前提となるため、基本的に必須とする。

ただし、`0-10_step1_start_checklist.md` はチェックリスト形式の補助資料であるため準必須とする。  
内容は簡易でよいが、STEP.1開始前の確認漏れを防ぐ目的で作成する。

## 6. STEP.1 成果物

STEP.1では、現行プログラムを整理し、STEP.2-1要件定義に進むためのインプットを作成する。

本プロジェクトでは、現行プログラムの元となるアルゴリズムが複雑であり、特に `NeighborhoodGraph` の処理理解が後続作業に影響する。  
そのため、STEP.1の成果物は個人プロジェクトとしてはやや厚めに作成する。

---

### 6-1. STEP.1 成果物一覧

| ファイル名 | 日本語名 | 区分 | 記載概要 |
|---|---|---|---|
| コメント整理済みソース | コメント整理済みソースコード | 必須 | 既存処理を変更せず、現行ソースコードのコメントを整理したもの。成果物は `src/` 配下のソースコード自体とする。 |
| `current_feature_list.md` | 現行機能一覧 | 必須 | 現行プログラムが持つ機能を一覧化する。入力、探索、出力、デバッグ、補助スクリプトなどの機能を整理する。 |
| `current_input_json_spec.md` | 現行入力JSON仕様 | 必須 | 現行JSONで定義できる項目、評価関数、制約、入力例、分かりにくい点、見直し候補を整理する。 |
| `current_process_flow.md` | 現行処理フロー | 必須 | 入力読み込みから探索、評価、出力までの全体処理フローを記載する。Markdown + Mermaidで作成する。 |
| `search_methods_overview.md` | 探索手法一覧 | 必須 | 近傍探索法、破壊法、修復法の一覧、各手法の概要、関連ファイル、探索全体での位置づけを整理する。 |
| `algorithm_implementation_mapping.md` | アルゴリズム・実装対応表 | 必須 | 卒論または元アルゴリズム上の概念と、現行ソースコード上のファイル・クラス・関数の対応関係を整理する。 |
| `neighborhood_graph_design_note.md` | NeighborhoodGraph詳細メモ | 必須 | 複雑な探索法である `NeighborhoodGraph` について、目的、管理データ、処理フロー、アルゴリズムとの対応を個別に整理する。 |
| `class_responsibility_list.md` | クラス責務一覧 | 準必須 | 主要クラスの役割、保持データ、関連クラス、責務の境界を整理する。 |
| `key_function_list.md` | 主要関数一覧 | 準必須 | 全関数ではなく、処理理解やリファクタリングに重要な主要関数のみを一覧化する。 |

---

### 6-2. STEP.1成果物の作成方針

STEP.1では、すべてを詳細化しすぎず、以下を重視する。

- 後から現行処理を理解できること
- STEP.2-1要件定義のインプットになること
- 焼きなまし法追加時に既存探索処理との関係を確認できること
- JSON入力見直しの判断材料になること
- Copilotによる設計・実装作業の参照資料になること

`current_feature_list.md` には、現行プログラムの機能を一覧化する。

### 6-4. `current_input_json_spec.md` の概要

`current_input_json_spec.md` には、現行JSON入力仕様を整理する。

主な記載内容は以下とする。

- JSONファイルの基本構造

`current_process_flow.md` には、現行プログラムの処理フローを整理する。

形式は **Markdown + Mermaid** とする。

主な記載内容は以下とする。

- プログラム全体フロー
- コマンドライン引数解析
- JSON読み込み
- 問題データ初期化
- 初期解生成
- 探索ループ
- 破壊法の選択・実行
- 修復法の選択・実行
- 近傍探索の実行
- 評価値計算
- 解の更新
- 終了条件判定
- 結果出力
- 関連ファイルとの対応

Mermaid図は、1つの図に詰め込みすぎず、以下のように分けて作成する。

- 全体フロー
- 探索ループ概要
- 入力処理フロー
- 出力処理フロー

### 6-7. `algorithm_implementation_mapping.md` の概要

`algorithm_implementation_mapping.md` には、アルゴリズム上の概念と実装箇所の対応を整理する。

主な記載内容は以下とする。

| 観点 | 記載内容 |
|---|---|
| アルゴリズム概念 | 例：解表現、評価値、破壊、修復、近傍探索、重み更新、終了条件 |
| 実装ファイル | 対応する `.cpp` / `.hpp` |
| 実装クラス | 対応するクラス |
| 実装関数 | 主要な関数 |
| 説明 | アルゴリズム上の役割と実装上の処理内容 |
| 注意点 | 実装固有の挙動、不明点、要確認事項 |

この成果物は、卒論や元アルゴリズムを後から見返した際に、現行コードのどこに対応するかを確認するために使用する。

### 6-8. `neighborhood_graph_design_note.md` の概要

`neighborhood_graph_design_note.md` は、`NeighborhoodGraph` に特化した詳細メモとする。

主な記載内容は以下とする。

- `NeighborhoodGraph` の目的
- 探索全体における位置づけ
- 関連ファイル
  - `src/Search/NeighborhoodGraph/NeighborhoodGraph.hpp`
  - `src/Search/NeighborhoodGraph/NeighborhoodGraph.cpp`
- 管理しているデータ
- 主要関数
- 処理フロー
- Mermaidによる処理図
- アルゴリズム上の概念との対応
- 他クラスとの関係
- リファクタリング時の注意点
- 不明点・要確認事項

`NeighborhoodGraph` は複雑な探索法であるため、コメント整理だけで済ませず、個別の設計メモとして残す。

また、`NeighborhoodGraph` は卒論で扱ったアルゴリズムと密接に関係する可能性があるため、ソースコードだけでは意図や概念対応が判断できない場合がある。

その場合は、推測で断定せず、要確認事項として記録する。

必要に応じて、後続レビューまたは追加作業で、卒論本文・卒論中の図・画像データなどの補足資料を参照して内容を補完する。

### 6-10. `key_function_list.md` の概要

`key_function_list.md` には、主要関数のみを整理する。

全関数を対象にすると作成コストが高いため、以下に該当する関数を中心に記載する。

- 入力読み込みに関わる関数
- 解生成に関わる関数
- 評価値計算に関わる関数
- 破壊法・修復法・近傍探索の中核関数
- `NeighborhoodGraph` の主要関数
- 出力に関わる関数
- 焼きなまし法追加時に影響しそうな関数

記載項目は以下とする。

| 項目 | 内容 |
|---|---|
| 関数名 | 関数名 |
| 所属ファイル | `.cpp` / `.hpp` |
| 所属クラス | クラス名 |
| 役割 | 何をする関数か |
| 入力 | 主な引数 |
| 出力 | 戻り値または更新内容 |
| 注意点 | 副作用、前提条件、要確認事項 |

## 7. STEP.2 成果物

STEP.2では、要件定義、基本設計、実装、テストに関する成果物を作成する。

STEP.2の成果物は、個人プロジェクトとして過剰にならないようにしつつ、リファクタリング後の判断理由と確認結果が残る粒度で作成する。

---

### 7-1. STEP.2 成果物一覧

| ファイル名 | 日本語名 | 区分 | 記載概要 |
|---|---|---|---|
| `requirements.md` | 要件定義書 | 必須 | STEP.2-1の成果物。機能要件、非機能要件、既存機能維持要件、対象外事項、受入条件を記載する。 |
| `basic_design.md` | 基本設計書 | 必須 | STEP.2-2の成果物。リファクタリング後の構成、主要クラス、処理方針、既存機能との関係を記載する。 |
| `json_input_review.md` | JSON入力見直し結果 | 必須 | 現行JSON構造の評価、変更要否、変更する場合の方針、変更しない場合の理由を記載する。 |
| `simulated_annealing_design.md` | 焼きなまし法設計書 | 準必須 | 焼きなまし法の追加設計を記載する。内容が短ければ `basic_design.md` に統合してもよい。 |
| `implementation_summary.md` | 実装内容まとめ | 必須 | STEP.2-3の成果物。変更したファイル、追加機能、リファクタリング内容、既存機能への影響を記載する。 |
| `test_checklist.md` | テストチェックリスト | 必須 | STEP.2-4のテスト設計成果物。確認観点、テストケース、実行手順、期待結果を記載する。 |
| `test_result.md` | テスト結果 | 必須 | STEP.2-4のテスト実施結果。実施環境、実施結果、確認結果、不具合、未確認事項を記載する。 |

---

### 7-2. STEP.2成果物の作成方針

STEP.2では、以下を重視する。

- 焼きなまし法追加の要件と設計を明確にする
- 既存機能を壊していないことを確認できるようにする
- JSON入力構造を変更するかどうかの判断理由を残す
- 実装変更の影響範囲を確認できるようにする
- テスト観点とテスト結果を分けて管理する

### 7-5. `json_input_review.md` の概要

`json_input_review.md` には、JSON入力構造の見直し結果を記載する。

主な記載内容は以下とする。

- 現行JSON構造の概要
- 現行JSONの分かりにくい点
- 入力ミスが起きやすい箇所
- 変更候補
- 変更する場合の新構造案
- 変更しない場合の判断理由
- 後方互換性の扱い
- READMEやテンプレートで補足すべき内容

本プロジェクトでは、JSON構造の見直しは「必ず変更する」ではなく、確認のうえで必要があれば変更する扱いとする。  
変更しない場合でも、変更不要と判断した理由をこのファイルに残す。

## 12. 成果物作成時の注意

### 12-1. 英語ファイル名と日本語内容の対応

ファイル名はGitHubやCLIで扱いやすいように英語名とする。  
ただし、ファイル本文は日本語で記載する。

各成果物の冒頭には、必ず以下を記載する。

```markdown
# 日本語の成果物名

## 目的

このファイルの目的を記載する。

## 概要

このファイルに何を記載するかを説明する。
```

例：

```markdown
# 現行処理フロー

## 目的

現行プログラムの入力から出力までの処理フローを整理し、STEP.2以降の要件定義・設計・実装時に参照できるようにする。

## 概要

本ファイルでは、プログラム全体の処理フロー、探索ループ、主要処理と関連ファイルの対応を記載する。
```

---

### 12-2. Mermaidの扱い

処理フローや複雑なアルゴリズム説明には、Markdown内にMermaidを使用する。

対象ファイルは主に以下とする。

- `current_process_flow.md`
- `neighborhood_graph_design_note.md`
- 必要に応じて `basic_design.md`

Mermaid図を作成する場合は、以下を守る。

- 1つの図に詰め込みすぎない
- 図は「全体」「詳細」「分岐」などに分ける
- ノード名は短くする
- 詳細な説明は図ではなく本文に書く
- 図と本文の対応が分かるようにする

---

### 12-3. 個人プロジェクトとしての粒度

本プロジェクトは個人プロジェクトであるため、成果物を過度に細かくしすぎない。

ただし、以下は必ず残す。

- 次工程のインプット
- 判断理由
- 複雑な処理の理解資料
- Copilotへの作業指示
- テスト観点
- テスト結果
