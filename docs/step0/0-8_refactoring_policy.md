# リファクタリング方針

## 1. 目的

本項目では、「卒論プログラムリファクタリング」プロジェクトにおけるリファクタリング方針を定義する。

本プロジェクトでは、卒論で作成した現行プログラムを整理し、可読性・保守性を向上させたうえで、卒論時点で今後の課題としていた機能改善を実施する。

主な対象は以下である。

- 現行ソースコードのコメント整備
- JSON入力構造・入力方法の見直し
- 現行ALNSへの焼きなまし法の考え方の組み込み
- 今後の修正・機能追加を行いやすくするための構造改善

---

## 2. 基本方針

本プロジェクトのリファクタリングでは、既存機能の維持を前提とする。

現行プログラムは、多様なグループ分け問題に対するC++製の最適化ソルバープログラムであり、JSONで問題定義や評価関数を入力することで、複数種類のグループ分け問題に対応できる構成になっている。

そのため、リファクタリングでは以下を基本方針とする。

- 既存ALNSの機能を原則維持する。
- 既存JSON入力との互換性を重視する。
- 評価関数をソースコード側に固定しない。
- 既存の破壊法、修復法、近傍探索、評価値計算を可能な限り活用する。
- 大規模な再設計ではなく、必要箇所を中心に段階的に改善する。
- STEP.1では既存処理を変更しない。
- STEP.2では、要件定義・基本設計に基づいて処理変更を行う。
- ソースコードの文字コードはCP932のまま維持する。
- 大規模な機械的整形は行わない。

---

## 3. リファクタリングで重視する観点

| 観点 | 方針 |
|---|---|
| 既存機能維持 | 現行ALNSの実行方法・入力・出力を可能な限り維持する。 |
| 可読性向上 | コメント整備により、処理内容、アルゴリズム上の役割、分岐条件を理解しやすくする。 |
| 保守性向上 | 今後の修正・機能追加時に影響範囲を把握しやすい構成にする。 |
| 入力改善 | JSON入力構造・入力方法を見直す。ただし変更を前提とはしない。 |
| 機能改善 | 焼きなまし法の考え方を現行ALNSへ組み込む。 |
| 検証可能性 | 既存機能と追加機能の動作確認・性能比較を行える状態にする。 |

---

## 4. STEP別方針

### 4-1. STEP.0

STEP.0では、プロジェクト準備、環境整備、方針決定を行う。

原則として、ソースコードの処理変更は行わない。

主な作業は以下とする。

- プロジェクト目的・ゴール定義
- 対象プログラム概要整理
- 現行プログラム保全
- GitHub Copilot利用環境整備
- 開発環境・実行環境整理
- 成果物一覧定義
- 作業ルール定義
- リファクタリング方針定義

---

### 4-2. STEP.1

STEP.1では、現行プログラム整理を行う。

STEP.1では、既存処理を変更しない。  
許可する変更は、原則としてコメント整理とドキュメント作成のみとする。

主な作業は以下とする。

- 現行ソースコードのコメント整理
- 現行機能一覧の作成
- 現行入力JSON仕様の整理
- 現行処理フローの作成
- 探索手法一覧の作成
- アルゴリズム・実装対応表の作成
- `NeighborhoodGraph` 詳細メモの作成
- クラス責務一覧の作成
- 主要関数一覧の作成

STEP.1では、以下を禁止する。

- 既存処理の変更
- アルゴリズムの変更
- 入力JSON仕様の変更
- 出力仕様の変更
- 関数名・クラス名・変数名の変更
- 大規模なコード整形

---

### 4-3. STEP.2-1

STEP.2-1では、要件定義を行う。

この段階では、リファクタリング後に満たすべき要件を定義する。  
原則として、ソースコードの処理変更は行わない。

主な作業は以下とする。

- 機能要件の整理
- 非機能要件の整理
- 既存機能維持要件の整理
- 焼きなまし法組み込み要件の整理
- JSON入力見直し要件の整理
- 対象外事項の整理
- 受入条件の整理

---

### 4-4. STEP.2-2

STEP.2-2では、基本設計を行う。

STEP.2-1で定義した要件に基づき、リファクタリング後の構成や実装方針を設計する。

主な作業は以下とする。

- 基本設計書の作成
- 焼きなまし法組み込み設計
- JSON入力見直し方針の設計
- 既存ALNSとの関係整理
- 変更対象ファイルの整理
- 変更しないファイルの整理
- READMEの初回更新

ソースコードの本格的な処理変更は、STEP.2-3で行う。

---

### 4-5. STEP.2-3

STEP.2-3では、リファクタリング実装を行う。

STEP.2-1の要件定義およびSTEP.2-2の基本設計に基づいて、必要な範囲でソースコードを変更する。

主な作業は以下とする。

- 現行ALNSへの焼きなまし法の考え方の組み込み
- JSON入力処理の見直し
- 必要に応じたコード構造改善
- 必要に応じたREADME更新
- 実装内容まとめの作成

実装時は、既存機能を壊さないことを重視する。

---

### 4-6. STEP.2-4

STEP.2-4では、テストを行う。

主な作業は以下とする。

- テストチェックリスト作成
- 既存ALNSの回帰確認
- 焼きなまし法組み込み後の動作確認
- JSON入力確認
- 必要に応じた性能比較
- テスト結果記録
- 不具合修正

---

## 5. コメント整備方針

コメント整備は、STEP.1で実施する。

目的は、現行処理を後から理解しやすくすることであり、処理そのものを変更することではない。

### 5-1. コメント整備の対象

コメント整備の対象は、主に以下とする。

- アルゴリズム上重要な処理
- 評価値計算
- 制約処理
- 分岐条件
- 破壊法
- 修復法
- 近傍探索
- `NeighborhoodGraph`
- JSON入力処理
- 出力処理

### 5-2. コメント整備時のルール

コメント整備時は、以下を守る。

- 処理内容を変更しない。
- 関数名、クラス名、変数名を変更しない。
- 文字コードをCP932のまま維持する。
- コメントは原則として日本語で記載する。
- 自明な処理に過剰なコメントを付けない。
- コードから読み取れない仕様を推測で断定しない。
- 不明点はTODOコメントまたはドキュメント上の要確認事項として残す。

---

## 6. JSON入力見直し方針

JSON入力は見直し対象とするが、変更を前提とはしない。

現行プログラムは、JSONで問題定義や評価関数を入力することで、複数種類のグループ分け問題に対応できる構成になっている。  
そのため、JSON構造を変更する場合は、影響範囲を慎重に確認する。

### 6-1. 見直し観点

JSON入力の見直しでは、以下を確認する。

- 現行JSONで定義できる内容
- 現行JSONの分かりにくい点
- 入力ミスが起きやすい箇所
- 評価関数の定義方法
- 制約条件の定義方法
- 焼きなまし法のパラメータをJSONに含める必要があるか
- 既存JSONとの後方互換性
- `template_json.json` の更新要否
- READMEで補足すべき内容

### 6-2. 変更判断

JSON入力については、以下の方針で判断する。

| 判断 | 方針 |
|---|---|
| 現行構造で問題ない | 変更せず、変更不要と判断した理由を `json_input_review.md` に記録する。 |
| 構造に改善余地がある | 改善案、影響範囲、後方互換性を整理したうえで変更する。 |
| 説明不足が主な問題 | JSON構造は変更せず、READMEやテンプレートの説明を改善する。 |
| 焼きなまし法パラメータが必要 | JSONに含めるか、CLIオプションにするかをSTEP.2-1で判断する。 |

---

## 7. 焼きなまし法組み込み方針

本プロジェクトでは、焼きなまし法を現行ALNSとは別の独立した探索アルゴリズムとして追加するのではなく、**現行ALNSの大枠に焼きなまし法の考え方を組み込む**。

つまり、焼きなまし法専用の独立クラスを追加して別アルゴリズムとして扱うのではなく、現行ALNSの探索ループや解の受理判定に、焼きなまし法の要素を取り入れる方針とする。

### 7-1. 組み込み対象

主な組み込み対象は以下とする。

- 解の受理判定
- 温度管理
- 冷却スケジュール
- 必要に応じた終了条件
- 必要に応じたログ・出力項目

### 7-2. 活用する既存処理

焼きなまし法の組み込みでは、可能な限り既存処理を活用する。

| 既存処理 | 方針 |
|---|---|
| 破壊法 | 既存の破壊法を活用する。 |
| 修復法 | 既存の修復法を活用する。 |
| 近傍探索 | 既存の近傍探索を必要に応じて活用する。 |
| 評価値計算 | 既存の評価値計算機構を活用する。 |
| 解表現 | 既存の `Solution` 周辺の構造を活用する。 |
| 乱数処理 | 既存の乱数処理を確認し、可能であれば活用する。 |

### 7-3. 設計時に決める事項

焼きなまし法の具体的な組み込み方法は、STEP.2-1およびSTEP.2-2で詳細化する。

主な未決定事項は以下である。

| 未決定事項 | 検討内容 |
|---|---|
| 受理判定を入れる位置 | ALNS探索ループのどの時点に入れるか。 |
| 初期温度 | 固定値にするか、評価値などから算出するか。 |
| 冷却スケジュール | 指数冷却、線形冷却など、どの方式にするか。 |
| 終了条件との関係 | 既存終了条件に温度条件を加えるか。 |
| パラメータ指定方法 | JSON、CLI、定数、設定ファイルのいずれにするか。 |
| 既存受理判定との関係 | 現行の解更新条件を置き換えるか、拡張するか。 |
| ログ出力 | 温度、受理率などを出力するか。 |
| テスト方法 | 何回実行し、どの指標を見るか。 |

## 8. デバッグ・グラフ描画関連の方針

デバッグモードおよびグラフ描画関連機能は、原則としてリファクタリング主対象外とする。

これらは卒論作成時の個人利用を目的に作成した補助機能であり、通常利用者向け機能として整備することは想定しない。  
また、デバッグモードでの実行は性能が劣化するため、通常実行や他利用者向け利用の前提にはしない。

### 8-1. 対象機能

以下は、原則として変更しない。

- `src/Debug/Debug.hpp`
- `src/Debug/Debug.cpp`
- `src/include/matplotlib.hpp`
- `src/DrawGraph/draw_graph.py`
- デバッグモードのグラフ描画機能

### 8-2. 修正する条件

以下の場合のみ、必要最小限の修正を行う。

- リファクタリングにより既存構造が変わり、デバッグモードがビルドできなくなる場合
- リファクタリングにより既存構造が変わり、デバッグモードが実行できなくなる場合
- 依存関係変更により、通常ビルドに影響が出る場合

### 8-3. テスト上の扱い

デバッグモードは、通常機能の必須確認対象には含めない。

必要に応じて、補助的に確認する。

## 9. コード構造改善方針

コード構造の改善は、必要箇所を中心に段階的に行う。

本プロジェクトでは、既存機能を維持しながら焼きなまし法の考え方を組み込むことを優先する。  
そのため、全体を大きく作り直すような再設計は原則として行わない。

### 9-1. 許容する改善

以下は、必要に応じて実施する。

- 重複処理の整理
- 責務が分かりにくい処理の分割
- 焼きなまし法組み込みに必要な処理の抽出
- 設定値やパラメータの整理
- 可読性を上げるための局所的な構造改善
- 必要最小限の関数分割
- 必要最小限のREADME更新

### 9-2. 慎重に扱う改善

以下は、影響範囲が大きいため慎重に扱う。

- クラス構造の大幅変更
- 主要クラス名の変更
- 主要関数名の変更
- 入力JSON構造の変更
- 出力形式の変更
- 乱数処理の変更
- 評価値計算の変更
- 大規模なファイル移動
- 大規模な自動整形

### 9-3. 原則行わない改善

以下は、本プロジェクトでは原則行わない。

- GUI化
- 厳密解法の追加
- JSON以外の入力形式への全面移行
- macOS正式対応
- デバッグ・グラフ描画機能の通常利用者向け整備
- ソースコードのUTF-8化
- 大規模な機械的フォーマット変更

---

## 10. 既存機能維持方針

既存機能は原則として維持する。

特に以下は、リファクタリング後も維持することを基本とする。

| 項目 | 方針 |
|---|---|
| 既存ALNS実行 | 維持する。 |
| 既存JSON入力 | 可能な限り維持する。 |
| CLI実行 | 維持する。 |
| 評価値出力 | 維持する。 |
| グループ分け結果出力 | 維持する。 |
| 実行時間出力 | 維持する。 |
| OpenMP | 推奨設定として維持する。 |
| CP932 | 維持する。 |
| `Data/A-n32-k5.json` による実行 | 維持する。 |

## 11. 性能比較方針

性能比較は、可能であれば実施する。

比較対象は、現行ALNSと焼きなまし法組み込み後のALNSとする。

### 11-1. 比較指標

現時点では、以下を比較指標とする。

| 指標 | 内容 |
|---|---|
| 評価値 | 複数回実行したときの平均評価値 |
| 実行時間 | 複数回実行したときの平均実行時間 |

### 11-2. 比較方法

具体的な比較方法は、STEP.2-4のテスト設計時に決定する。

主な検討事項は以下である。

- 実行回数
- 対象入力JSON
- 平均以外の統計量を確認するか
- 現行ALNSとの比較方法
- 焼きなまし法組み込み後ALNSとの比較方法
- 実行環境
- OpenMP有無の扱い

### 11-3. 記録先

性能比較結果は、原則として `test_result.md` に記録する。

比較内容が多くなる場合は、必要に応じて以下のファイルを追加する。

```text
docs/step2/performance_comparison.md
```

## 12. README更新方針

READMEは、仕様が固まった後に更新する。

初回更新タイミングは、STEP.2-2 基本設計の終盤を目安とする。  
以降、実装・テストの過程で仕様、実行方法、入力形式、オプションに変更が発生した場合は、必要に応じてREADMEを更新する。

READMEに反映する主な内容は以下とする。

- プログラム概要
- ビルド方法
- 実行方法
- 入力JSONの仕様
- 実行オプション
- ALNSと焼きなまし法組み込み後の利用方法
- デバッグモードの位置づけ
- サンプル実行
- 注意事項

---

## 13. テスト方針との関係

リファクタリング方針は、STEP.2-4のテスト方針に反映する。

最低限、以下を確認する。

- 既存ALNSが動作すること
- 焼きなまし法の考え方を組み込んだALNSが動作すること
- `Data/A-n32-k5.json` を使って実行できること
- 評価値が出力されること
- グループ分け結果が出力されること
- 実行時間が出力されること
- JSON入力を変更した場合、変更後の入力で実行できること
- JSON入力を変更しない場合、変更不要と判断した理由が記録されていること

探索には乱数が関係するため、実行結果の完全一致は必須確認としない。
