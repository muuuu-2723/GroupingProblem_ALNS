# 作業ルール定義

## 1. 目的

本項目では、「卒論プログラムリファクタリング」プロジェクトを進めるうえでの作業ルールを定義する。

本プロジェクトでは、ChatGPTとGitHub Copilotを併用して作業を進めるため、以下を明確にする。

- Gitブランチ運用
- コミットメッセージ規則
- コミット単位
- GitHub Copilot Agent Modeの利用ルール
- レビュー指摘票の運用
- ドキュメント更新ルール
- README更新ルール
- ビルド・実行確認ルール
- 文字コード維持ルール
- コード整形ルール
- STEP別の変更許可範囲

---

## 2. 基本方針

本プロジェクトでは、以下を基本方針とする。

- `master` ブランチでは直接作業しない。
- 作業はSTEPごとの作業ブランチで行う。
- 1コミットには1つの目的の変更のみを含める。
- GitHub Copilot Agent Modeは、原則として作業ブランチ上で使用する。
- Copilotによる変更後は、必ず差分を確認する。
- STEP.1では、既存処理を変更しない。
- 仕様変更や設計変更は、実装前にドキュメントへ反映する。
- ソースコードの文字コードはCP932のまま維持する。
- レビュー指摘は、誤字や軽微な修正も含めてレビュー指摘票に記録する。

---

## 3. Gitブランチ運用

### 3-1. ブランチ方針

`master` ブランチは、安定版・保全用ブランチとして扱う。

以降の作業は、STEPごとの作業ブランチで行う。

| ブランチ | 用途 |
|---|---|
| `master` | 安定版・保全用 |
| `step0/project-setup` | STEP.0 プロジェクト準備・方針決定 |
| `step1/current-code-analysis` | STEP.1 現行プログラム整理 |
| `step2/requirements` | STEP.2-1 要件定義 |
| `step2/design` | STEP.2-2 基本設計 |
| `step2/refactoring` | STEP.2-3 実装 |
| `step2/test` | STEP.2-4 テスト |

### 3-2. ブランチ作成タイミング

各ブランチは、該当STEPを開始するタイミングで作成する。

例：

```bash
git checkout master
git pull origin master
git checkout -b step1/current-code-analysis
git push -u origin step1/current-code-analysis
```

### 3-3. `master` の扱い

`master` ブランチでは直接作業しない。

`master` への反映は、各STEPの成果物確認後に行う。

### 3-4. リファクタリング前タグ

リファクタリング前の基準状態には、以下のタグを付与する。

```text
v0.0.0-before-refactoring
```

このタグは、現行プログラムを保全し、必要に応じてリファクタリング前の状態へ戻るために使用する。

## 4. コミットメッセージ規則

### 4-1. 基本形式

コミットメッセージは、以下の形式とする。

```text
prefix: 日本語の変更内容
```

prefixは英語で記載し、変更内容は日本語で記載する。

### 4-2. 使用するprefix

| prefix | 用途 |
|---|---|
| `docs:` | ドキュメント追加・修正 |
| `chore:` | 設定変更、不要ファイル削除、環境整備 |
| `comment:` | コメント整理のみ |
| `refactor:` | 振る舞いを変えないコード改善 |
| `feat:` | 機能追加 |
| `fix:` | バグ修正 |
| `test:` | テスト追加・修正 |
| `review:` | レビュー指摘票の追加・更新 |

### 4-3. コミットメッセージ例

```text
docs: 0-6成果物一覧を追加
docs: 0-7作業ルールを追加
chore: 不要なresult.txtを削除
comment: Solutionクラスのコメントを整理
refactor: Search基底クラスの責務を整理
feat: 焼きなまし法の探索処理を追加
fix: JSON入力時のエラー処理を修正
test: 焼きなまし法の動作確認ケースを追加
review: STEP1コメント整理の指摘票を追加
```

---

## 5. コミット単位

### 5-1. 基本ルール

1つのコミットには、1つの目的の変更のみを含める。

### 5-2. よいコミット単位

| 例 | 理由 |
|---|---|
| `docs: 0-7作業ルールを追加` | 1つの成果物追加に閉じている |
| `comment: Groupクラスのコメントを整理` | 1つのコメント整理作業に閉じている |
| `feat: 焼きなまし法のSearchクラスを追加` | 1つの機能追加単位になっている |
| `test: 既存ALNSの通常実行確認結果を追加` | 1つのテスト確認に閉じている |

### 5-3. 避けるコミット単位

| 例 | 理由 |
|---|---|
| ドキュメント追加とコード修正を同時に含める | 変更目的が混在する |
| コメント整理と処理変更を同時に含める | STEP.1の処理変更禁止ルールと衝突しやすい |
| 大量の整形変更と機能追加を同時に含める | 差分レビューが困難になる |
| 複数STEPの成果物を同時に含める | 履歴が追いにくくなる |

## 6. GitHub Copilot利用ルール

### 6-1. 基本方針

GitHub Copilotは、主にSTEP.1、STEP.2-2、STEP.2-3、STEP.2-4で使用する。

| STEP | Copilotの主な役割 |
|---|---|
| STEP.1-1 | 現行プログラムのコメント整理 |
| STEP.1-2 | 現行プログラムの設計書作成 |
| STEP.2-2 | 基本設計作成 |
| STEP.2-3 | リファクタリング実装 |
| STEP.2-4 | テストチェックリスト作成、テスト結果記録 |

### 6-2. Copilotへの指示

Copilotへの共通指示は、以下に記載する。

```text
.github/copilot-instructions.md
```

作業別プロンプトは、以下に保存する。

```text
.github/prompts/
```

### 6-3. 指示言語

Copilotへの指示、成果物、レビュー指摘票は原則として日本語で記載する。

ただし、以下は必要に応じて英語表記を併記する。

- クラス名
- 関数名
- 変数名
- ファイル名
- アルゴリズム名
- 技術用語

### 6-4. Copilotに任せない判断

以下はCopilotに丸投げせず、ユーザーまたはChatGPT側で判断する。

- プロジェクト目的の確定
- 要件定義の最終判断
- JSON入力構造を変更するかどうかの判断
- 焼きなまし法の追加方針の確定
- 既存仕様を変更するかどうかの判断
- `master` ブランチへのマージ判断
- 大規模な設計変更の採否判断

## 7. Agent Mode利用ルール

### 7-1. 基本方針

本プロジェクトでは、可能な限りGitHub Copilot Agent Modeを使用する。

Agent Modeは、複数ファイルを横断して調査・編集・確認を行う作業に使用する。

### 7-2. 使用する作業例

- コメント整理
- 現行設計書作成
- 現行処理フロー作成
- `NeighborhoodGraph` の詳細整理
- 基本設計作成
- 複数ファイルをまたぐリファクタリング
- テストチェックリスト作成
- レビュー指摘票に基づく修正対応

### 7-3. 使用時のルール

Agent Modeを使用する際は、以下を守る。

- `master` ブランチでは使用しない。
- STEPごとの作業ブランチ上で使用する。
- 1回の作業範囲を大きくしすぎない。
- 作業前に対象ファイルと目的を明示する。
- 既存処理を変更しない作業では、変更禁止事項を明記する。
- 不明点を推測で実装させない。
- 変更後は必ず差分を確認する。
- 可能な場合はビルド確認を行う。
- 実行可能な場合はサンプルJSONで動作確認する。
- 仕様変更を伴う修正は、事前に要件定義または設計書へ反映する。

## 8. レビュー指摘票運用

### 8-1. 基本方針

レビュー指摘は、誤字や軽微な修正も含めて、原則としてレビュー指摘票に記録する。

ただし、1指摘ごとに1ファイルを作成するのではなく、レビュー対象や作業単位ごとに1つの指摘票を作成し、その中に複数指摘をまとめる。

### 8-2. レビュー指摘票の配置

レビュー指摘票は、以下に保存する。

```text
docs/reviews/
```

STEP別に以下のディレクトリへ配置する。

```text
docs/reviews/step1/
docs/reviews/step2/
```

### 8-3. レビュー指摘票の命名規則

レビュー指摘票は以下の命名規則とする。

```text
REV-{STEP番号}-{連番}_{対象作業}.md
```

例：

```text
REV-STEP1-001_comment-cleanup.md
REV-STEP1-002_current-process-flow.md
REV-STEP1-003_neighborhood-graph-note.md
REV-STEP2-001_requirements.md
REV-STEP2-002_basic-design.md
REV-STEP2-003_refactoring.md
REV-STEP2-004_test.md
```

### 8-4. 指摘票に記録する内容

レビュー指摘票には、以下を記載する。

- 指摘票ID
- 対象STEP
- 対象成果物
- 作成日
- レビュー実施者
- 修正担当
- ステータス
- 指摘番号
- 対象ファイル
- 対象箇所
- 指摘区分
- 指摘内容
- 修正方針
- 対応状況

### 8-5. 指摘区分

指摘区分は以下を使用する。

| 指摘区分 | 内容 |
|---|---|
| 誤字 | 文字の誤り |
| 表記ゆれ | 用語や表現の不統一 |
| 表現修正 | 分かりにくい表現の修正 |
| Markdown修正 | Markdown構文、表、見出し、コードブロックの修正 |
| Mermaid修正 | Mermaid図の構成・表示・見やすさの修正 |
| 不足 | 必要な情報が不足している |
| 誤り | 内容に誤りがある |
| 構成修正 | 章立てや記載順の修正 |
| 仕様不明 | 仕様の確認が必要 |
| 要確認 | ユーザー判断が必要 |
| その他 | 上記に該当しない指摘 |

### 8-6. Copilotによる修正対応

レビュー指摘票に基づいてCopilotに修正させる場合は、以下を使用する。

```text
.github/prompts/review-fix.prompt.md
```

Copilotには、以下を読み込ませる。

- `.github/prompts/review-fix.prompt.md`
- 対象のレビュー指摘票

修正後は、指摘番号ごとに対応内容を確認し、指摘票のステータスを更新する。

## 9. Copilot作業後の確認手順

Copilotによる作業後は、以下を確認する。

### 9-1. 差分確認

```bash
git status
git diff
```

確認項目：

- 意図しないファイルが変更されていないか
- 指示対象外の仕様変更がないか
- コメント整理のみの作業で処理が変わっていないか
- Copilotの報告内容と実際の差分が一致しているか
- レビュー指摘票の内容に沿って修正されているか

### 9-2. 文字コード確認

確認項目：

- CP932のソースコードがUTF-8へ変換されていないか
- 日本語コメントが文字化けしていないか
- `Makefile` の文字コード設定と矛盾していないか

### 9-3. ビルド確認

可能な場合は以下を実行する。

```bash
make
```

### 9-4. 実行確認

通常実行確認には、以下のサンプルJSONを使用する。

```text
Data/A-n32-k5.json
```

WSL2の場合：

```bash
./bin/run.out -p Data/A-n32-k5.json
```

Windows cmdの場合：

```cmd
bin\run.exe -p Data\A-n32-k5.json
```

確認項目：

- 異常終了しないこと
- 評価値が表示されること
- グループ分け結果が表示されること
- 実行時間が表示されること

探索には乱数が関係するため、実行結果の完全一致は確認基準としない。

## 10. ドキュメント更新ルール

### 10-1. 基本方針

仕様・方針・設計が変わった場合は、コード実装より先に関連ドキュメントを更新する。

実装後に実態とドキュメントがずれた場合は、同じ作業内で修正する。

### 10-2. 更新対象の例

| 変更内容 | 更新対象 |
|---|---|
| JSON仕様変更 | `current_input_json_spec.md`, `json_input_review.md`, README |
| 探索法追加 | `search_methods_overview.md`, `basic_design.md`, `test_checklist.md` |
| 焼きなまし法追加 | `requirements.md`, `basic_design.md`, `simulated_annealing_design.md`, `test_checklist.md` |
| 実行オプション追加 | README, `0-5_development_environment.md`, `test_checklist.md` |
| クラス構成変更 | `class_responsibility_list.md`, `basic_design.md` |
| テスト観点追加 | `test_checklist.md` |
| テスト結果追加 | `test_result.md` |

## 11. README更新ルール

READMEは、仕様が固まった後に更新する。

初回更新タイミングは、STEP.2-2 基本設計の終盤を目安とする。

以降、実装・テストの過程で仕様、実行方法、入力形式、オプションに変更が発生した場合は、必要に応じてREADMEを更新する。

READMEに反映する主な内容は以下とする。

- プログラム概要
- ビルド方法
- 実行方法
- 入力JSONの仕様
- 実行オプション
- ALNSと焼きなまし法の利用方法
- デバッグモード
- サンプル実行
- 注意事項

## 12. ビルド・実行確認ルール

### 12-1. ビルド

通常のビルドは、リポジトリ直下で以下を実行する。

```bash
make
```

### 12-2. 実行

WSL2の場合：

```bash
./bin/run.out -p Data/A-n32-k5.json
```

Windows cmdの場合：

```cmd
bin\run.exe -p Data\A-n32-k5.json
```

### 12-3. 成功判定

実行成功の判断基準は以下とする。

- プログラムが異常終了しない
- コマンドライン上に解が出力される
- 評価値が表示される
- グループ分け結果が表示される
- 実行時間が表示される

正常終了時の終了コードは `0` である。

ただし、現行プログラムではC++標準の終了コード以外に独自の終了コード管理は行っていない。

## 13. 文字コードルール

現行ソースコードはCP932を前提とする。

そのため、以下を守る。

- ソースコードを勝手にUTF-8へ変換しない。
- コメント整理時もCP932を維持する。
- VS CodeやCopilotによる自動変換に注意する。
- 日本語コメントが文字化けしていないことを確認する。
- `Makefile` の `-finput-charset=CP932` を前提とする。

Windows環境では、Makefileにより以下も指定される。

```makefile
-fexec-charset=CP932
```

## 14. コード整形ルール

STEP.1では、既存フォーマットを維持する。

STEP.2のリファクタリング時も、広範囲の機械的フォーマット変更は避ける。

整形を行う場合は、以下を守る。

- 変更対象の処理に関係する範囲に限定する。
- 機能追加や仕様変更と大量整形を同じコミットに含めない。
- 差分確認が困難になる整形は避ける。
- `clang-format` 等の自動整形を導入する場合は、別途方針を決める。

## コメント記述ルール

STEP.1のコメント整理では、コメントの粒度と形式をある程度統一する。

主要クラス・主要関数には、必要に応じてDoxygen風のコメント形式を使用する。

ただし、全クラス・全関数に対して機械的にDoxygenコメントを付与することは必須としない。

コメント付与の優先対象は以下とする。

- アルゴリズム上重要なクラス・関数
- 評価値計算に関係する処理
- 解の更新に関係する処理
- 破壊法・修復法・近傍探索の中核処理
- JSON入力処理
- 副作用がある処理
- 前提条件が分かりにくい処理

自明なgetter/setterや短い単純処理には、冗長なコメントを付けない。

処理意図が不明な場合は、推測で断定せず、`TODO: 要確認` コメントまたはドキュメント上の要確認事項として残す。

## 15. STEP別変更許可範囲

### 15-1. STEP.0

STEP.0では、プロジェクト準備、環境整備、方針決定を行う。

許可する変更：

- `docs/step0/` の作成・更新
- `.github/copilot-instructions.md` の作成・更新
- `.github/prompts/` の作成・更新
- `docs/reviews/` の作成・更新
- `.gitignore` の整理
- 不要ファイルの削除
- Git運用に必要な設定整理

原則として、ソースコードの処理変更は行わない。

### 15-2. STEP.1

STEP.1では、現行プログラム整理を行う。

許可する変更：

- コメント整理
- `docs/step1/` の作成・更新
- 現行機能一覧の作成
- 現行入力JSON仕様の整理
- 現行処理フローの作成
- 探索手法一覧の作成
- アルゴリズム・実装対応表の作成
- `NeighborhoodGraph` 詳細メモの作成
- クラス責務一覧・主要関数一覧の作成

禁止する変更：

- 既存処理の変更
- アルゴリズムの変更
- 入力JSON仕様の変更
- 出力仕様の変更
- 関数名・クラス名・変数名の変更
- 大規模なコード整形

### 15-3. STEP.2-1

STEP.2-1では、要件定義を行う。

許可する変更：

- `docs/step2/requirements.md` の作成・更新
- `docs/step2/json_input_review.md` の作成・更新
- 既存機能維持要件の整理
- 焼きなまし法追加要件の整理
- JSON入力見直し方針の整理
- 受入条件の整理

原則として、ソースコードの処理変更は行わない。

### 15-4. STEP.2-2

STEP.2-2では、基本設計を行う。

許可する変更：

- `docs/step2/basic_design.md` の作成・更新
- `docs/step2/simulated_annealing_design.md` の作成・更新
- READMEの初回更新
- 設計に必要な補足資料の作成

ソースコードの本格的な処理変更は、STEP.2-3で行う。

### 15-5. STEP.2-3

STEP.2-3では、リファクタリング実装を行う。

許可する変更：

- ソースコードのリファクタリング
- 焼きなまし法の実装
- JSON入力処理の見直し
- 実行オプションの追加・修正
- 必要なREADME更新
- `implementation_summary.md` の作成・更新

注意事項：

- 要件定義・基本設計に基づいて変更する。
- 既存機能が壊れていないことを確認する。
- 実装内容は `implementation_summary.md` に記録する。

### 15-6. STEP.2-4

STEP.2-4では、テストを行う。

許可する変更：

- `test_checklist.md` の作成・更新
- `test_result.md` の作成・更新
- 必要に応じた `performance_comparison.md` の作成・更新
- テストに必要な入力JSONの追加
- テストコードの追加
- テストで発見した不具合の修正
- 必要なREADME更新

注意事項：

- テスト観点・テストケース・期待結果は `test_checklist.md` に記録する。
- 実際の実行結果・判定・未確認事項は `test_result.md` に記録する。
- 不具合修正は、可能な限り `fix:` コミットとして分ける。
- テスト結果は、実際に確認した内容のみ記録する。

---

## 16. 作業完了条件

各作業は、以下を満たした時点で完了とする。

- 対象成果物が作成または更新されている。
- 必要なレビュー指摘票が作成・更新されている。
- Copilotを使用した場合、差分確認が完了している。
