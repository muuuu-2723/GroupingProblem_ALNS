# GitHub Copilotへの指示テンプレート

## 1. 目的

本項目では、GitHub Copilot Agent Mode に作業を依頼するための指示テンプレートを定義する。

本プロジェクトでは、Copilotを主に以下の作業で使用する。

- STEP.1-1 現行プログラムのコメント整理
- STEP.1-2 現行プログラムの設計書作成
- STEP.2-2 基本設計
- STEP.2-3 リファクタリング実装
- STEP.2-4 テストチェックリスト作成
- STEP.2-4 テスト結果記録
- レビュー指摘票に基づく修正対応

Copilotへの指示は、原則として日本語で記載する。

---

## 2. プロンプト管理方針

Copilotへの指示は、`.github/prompts/` 配下のプロンプトファイルとして管理する。

プロンプトファイルは、後続プロジェクトでも再利用できるよう、作業単位ごとに分割する。

### 2-1. プロンプトファイル一覧

| ファイル名 | 用途 |
|---|---|
| `.github/prompts/step1-comment-cleanup.prompt.md` | STEP.1-1 コメント整理 |
| `.github/prompts/step1-current-design-doc.prompt.md` | STEP.1-2 現行設計書作成 |
| `.github/prompts/step1-neighborhood-graph-analysis.prompt.md` | STEP.1 `NeighborhoodGraph` 詳細整理 |
| `.github/prompts/step2-basic-design.prompt.md` | STEP.2-2 基本設計 |
| `.github/prompts/step2-refactoring.prompt.md` | STEP.2-3 リファクタリング実装 |
| `.github/prompts/step2-test-checklist.prompt.md` | STEP.2-4 テストチェックリスト作成 |
| `.github/prompts/step2-test-result.prompt.md` | STEP.2-4 テスト結果記録 |
| `.github/prompts/review-fix.prompt.md` | レビュー指摘票に基づく修正対応 |

## 3. プロンプト変数の利用方針

Copilotプロンプトでは、依頼ごとに変わる対象ファイル・対象ドキュメント・レビュー指摘票などは `${input:...}` で変数化する。

一方で、作業条件、追加条件、変更許可範囲、変更禁止事項、重点確認観点は変数化しない。

これらは、プロンプトファイル、設計書、レビュー指摘票、テストチェックリストなど、Git管理されるファイルに明記する。

理由は、チャット上で入力した追加条件がGit履歴に残らず、後から作業根拠を追跡しにくくなるためである。

### 3-1. 変数化するもの

| 項目 | 例 |
|---|---|
| 対象ファイル | `${input:target_files}` |
| 対象ドキュメント | `${input:target_documents}` |
| 対象設計書 | `${input:design_document}` |
| レビュー指摘票 | `${input:review_ticket_file}` |
| テストチェックリスト | `${input:test_checklist_file}` |
| テスト結果ファイル | `${input:test_result_file}` |
| テスト対象 | `${input:test_target}` |
| 使用する入力ファイル | `${input:input_files}` |

### 3-2. 変数化しないもの

| 項目 | 管理先 |
|---|---|
| 追加条件 | 設計書、レビュー指摘票、テストチェックリスト |
| 変更してよい範囲 | 設計書、レビュー指摘票 |
| 変更禁止事項 | プロンプト本文、作業ルール、レビュー指摘票 |
| 重点的に確認する観点 | プロンプト本文、対象成果物、レビュー指摘票 |
| 設計判断の前提 | 要件定義書、基本設計書 |
| テスト実行回数 | テストチェックリスト |
| 性能比較条件 | テストチェックリスト |

## 4. 共通指示

すべてのCopilot作業では、以下を共通ルールとする。

```markdown
# 共通指示

あなたは「卒論プログラムリファクタリング」プロジェクトの作業支援担当です。

このプロジェクトは、卒論で作成したC++製のグループ分け問題ソルバーを整理し、可読性・保守性を向上させたうえで、現行ALNSに焼きなまし法の考え方を組み込むことを目的としています。

## 基本ルール

- 指示された作業範囲を超えて変更しないでください。
- 不明点を推測で実装・記述しないでください。
- 不明点は「要確認事項」として報告してください。
- 既存仕様を変更する場合は、必ず変更理由を説明してください。
- ソースコードを変更する場合は、処理内容・影響範囲・確認方法を報告してください。
- ドキュメントを作成する場合は、日本語で記述してください。
- コードコメントも原則として日本語で記述してください。
- クラス名、関数名、変数名、ファイル名、技術用語は必要に応じて英語表記を維持してください。
- 現行ソースコードの文字コードはCP932前提です。勝手にUTF-8へ変換しないでください。
- STEP.1では既存処理を変更しないでください。
- 大規模な自動整形は行わないでください。
- 変更後は、変更ファイルと変更内容を要約してください。
```

## 5. `.github/copilot-instructions.md`

`.github/copilot-instructions.md` には、リポジトリ全体に適用する共通指示を記載する。

```markdown
# GitHub Copilot Instructions

## プロジェクト概要

このリポジトリは、多様なグループ分け最適化問題を対象とした C++ 製ソルバープログラムです。

本プログラムは、JSON ファイルからグループ分け問題の定義を読み込み、Adaptive Large Neighborhood Search（ALNS）および近傍探索を用いて近似解を探索します。

本プロジェクトの目的は、卒論で作成した現行プログラムを整理し、可読性・保守性を向上させたうえで、現行 ALNS に焼きなまし法の考え方を組み込むことです。

## 基本方針

- 説明、コメント、ドキュメントは原則として日本語で記述してください。
- 技術用語、クラス名、関数名、変数名、ファイル名、アルゴリズム名は必要に応じて英語表記を維持してください。
- 明示的な指示がない限り、既存の処理仕様を変更しないでください。
- 入力形式の再設計を明示的に指示しない限り、既存の JSON 入力形式との互換性を維持してください。
- 評価関数をソースコード側に固定しないでください。
- 既存の破壊法、修復法、近傍探索、評価値計算は可能な限り活用してください。
- 仕様が不明な場合は推測で実装せず、要確認事項として報告してください。
- 変更は小さく、レビューしやすい単位にしてください。
- ソースコードを変更した場合は、変更したファイル、変更理由、既存仕様への影響を報告してください。
- コメントは有用で簡潔なものにしてください。冗長なコメントは避けてください。
- 既存のアルゴリズムを明示的な指示なしに削除しないでください。
- 大規模な自動整形は行わないでください。

## 開発環境

- 使用言語: C++
- C++標準: C++17
- コンパイラ: g++
- ビルド方法: Makefile
- 実行方式: CLI
- 入力形式: JSON
- 出力形式: コマンドライン表示
- 文字コード: CP932
- 確認済み環境: Windows cmd, WSL2

## 文字コード

現行ソースコードは CP932 を前提としています。

- ソースコードを勝手に UTF-8 へ変換しないでください。
- コメント整理時も CP932 を維持してください。
- 日本語コメントが文字化けしないように注意してください。
- `Makefile` の `-finput-charset=CP932` を前提としてください。
- Windows 環境では `-fexec-charset=CP932` も指定されています。

## プロジェクトの流れ

- STEP.0: プロジェクト準備、環境整備、方針決定
- STEP.1: 現行プログラムのコメント整理、分析、ドキュメント化
- STEP.2-1: 要件定義
- STEP.2-2: 基本設計の作成
- STEP.2-3: リファクタリングの実装
- STEP.2-4: テストの作成と実行

## STEP.1 の作業ルール

STEP.1 では、現行プログラム整理を行います。

- 既存処理を変更しないでください。
- アルゴリズムを変更しないでください。
- 入力 JSON 仕様を変更しないでください。
- 出力仕様を変更しないでください。
- 関数名、クラス名、変数名を変更しないでください。
- 大規模なコード整形は行わないでください。
- コメント整理とドキュメント作成のみを行ってください。
- コードから読み取れない仕様は推測で断定せず、要確認事項として記録してください。

## STEP.2 の作業ルール

STEP.2 では、要件定義・基本設計に基づいてリファクタリングを行います。

- 既存機能を壊さないようにしてください。
- 現行 ALNS の大枠を維持してください。
- 焼きなまし法は、独立した別アルゴリズムとして追加するのではなく、現行 ALNS の探索ループや受理判定へ考え方を組み込む方針です。
- 既存の破壊法、修復法、近傍探索、評価値計算は可能な限り活用してください。
- 要件定義・基本設計にない仕様変更は行わないでください。
- 仕様変更が必要な場合は、先に関連ドキュメントへ反映してください。

## Debug・グラフ描画関連の扱い

以下のファイル・機能は、原則としてリファクタリングの主対象外です。

- `src/Debug/Debug.hpp`
- `src/Debug/Debug.cpp`
- `src/include/matplotlib.hpp`
- `src/DrawGraph/draw_graph.py`
- デバッグモードのグラフ描画機能

これらは卒論作成時の個人利用を目的に作成した補助機能であり、通常利用者向けに整備する対象ではありません。

構造変更によりビルドできない、または利用できなくなる場合のみ、必要最小限で修正してください。

## Git・作業ブランチ

- `master` ブランチで直接作業しないでください。
- 作業は STEP ごとの作業ブランチで行ってください。
- 変更内容はコミット前に要約してください。
- 1つの変更では、目的の異なる修正を混在させないでください。

## ドキュメント

- ドキュメントは原則として日本語で記述してください。
- Markdown で記述してください。
- 処理フローや複雑なアルゴリズム説明では、必要に応じて Mermaid を使用してください。
- Mermaid 図は1つに詰め込みすぎず、全体フロー・詳細フローなどに分けてください。
- ファイル名、クラス名、関数名は英語表記のまま記載してください。

## レビュー指摘票

レビュー指摘は `docs/reviews/` 配下のレビュー指摘票で管理します。

レビュー指摘票に基づいて修正する場合は、以下を守ってください。

- 指摘票に記載された範囲を優先して修正してください。
- 指摘内容に含まれていない仕様変更は行わないでください。
- 指摘の意図が不明な場合は、推測で大きく変更せず、要確認事項として報告してください。
- 修正後、対応した指摘番号と対応内容を報告してください。

## 作業後の報告

作業後は、以下を報告してください。

- 変更したファイル
- 変更内容の概要
- 変更理由
- 既存仕様への影響
- ビルド確認の要否
- 実行確認の要否
- 文字コードを変更していないことの確認
- 不明点・要確認事項
```

````markdown
---
description: STEP.1-1 現行C++ソースコードのコメント整理

# 目的

現行プログラムの処理内容を後から理解しやすくするため、対象ソースコードのコメントを整理してください。

この作業は STEP.1-1 の「現行プログラムのコメント整理」に該当します。

# 対象ファイル

${input:target_files}

# 前提

本プロジェクトは、卒論で作成した C++ 製のグループ分け問題ソルバープログラムを整理し、可読性・保守性を向上させたうえで、現行 ALNS に焼きなまし法の考え方を組み込むことを目的としています。

STEP.1 では、既存処理を変更せず、現行プログラムの理解と整理を行います。

# 作業内容

対象ファイルを読み、既存処理を変更せずにコメントを整理してください。

以下を重点的にコメントしてください。

- アルゴリズム上重要な処理
- 評価値計算
- 制約処理
- 分岐条件
- ループの目的
- 破壊法・修復法・近傍探索の中核処理
- 副作用がある処理
- 前提条件がある処理
- `NeighborhoodGraph` のような複雑な処理
- JSON入力処理
- 出力処理

# コメント方針

- コメントは原則として日本語で記述してください。
- 自明な処理に過剰なコメントを付けないでください。
- コードから読み取れない仕様を推測で断定しないでください。
- 既存コメントが古い、誤解を招く、または実装と一致していない場合は修正してください。
- 不要または冗長なコメントは整理してください。
- アルゴリズム上の意図、前提条件、注意点が分かるコメントを優先してください。

# コメント形式

コメントの書き方は、以下の方針で統一してください。

## クラスコメント

主要クラスには、可能な範囲で以下の形式のコメントを付けてください。

```cpp
/**
 * @brief クラスの役割を簡潔に説明する。
 *
 * アルゴリズム上の位置づけ、保持する主な情報、他クラスとの関係など、
 * 後から処理を理解するために必要な補足を記載する。
 */
class ClassName {
    ...
};
```

## 関数コメント

主要関数には、可能な範囲で以下の形式のコメントを付けてください。

```cpp
/**
 * @brief 関数の役割を簡潔に説明する。
 *
 * 必要に応じて、処理の前提、アルゴリズム上の意味、副作用、注意点を記載する。
 *
 * @param arg1 引数の意味
 * @param arg2 引数の意味
 * @return 戻り値の意味
 */
ReturnType functionName(Type arg1, Type arg2);
```

## 通常コメント

処理中のコメントは、以下のように簡潔に記載してください。

```cpp
// 評価値が改善した場合は、現在解と最良解を更新する
```

## TODOコメント

処理意図が読み取れない場合や確認が必要な場合は、以下の形式で残してください。

```cpp
// TODO: 要確認 - この条件分岐の意図がコード上から判断できない
```

## コメント対象の優先順位

すべてのクラス・関数に機械的にコメントを付ける必要はありません。

優先順位は以下とします。

1. アルゴリズム上重要なクラス・関数
2. 評価値計算に関係するクラス・関数
3. 解の更新に関係するクラス・関数
4. 破壊法・修復法・近傍探索の中核処理
5. JSON入力処理
6. 副作用がある処理
7. 前提条件が分かりにくい処理

自明なgetter/setterや、処理内容が明らかな短い関数には、無理に詳細コメントを付けないでください。

# 制約

- 処理内容は変更しないでください。
- 関数名、クラス名、変数名は変更しないでください。
- 入力JSON仕様は変更しないでください。
- 出力仕様は変更しないでください。
- アルゴリズムは変更しないでください。
- 大規模なコード整形は行わないでください。
- 文字コードはCP932のまま維持してください。
- ソースコードをUTF-8へ変換しないでください。
- Debug関連・グラフ描画関連を対象に含める場合も、処理変更は行わないでください。

# 不明点の扱い

処理意図が不明な場合は、以下のいずれかで対応してください。

- `TODO: 要確認` コメントを残す
- 作業後の報告に「要確認事項」として記載する

推測で仕様を断定しないでください。

# 作業後の報告

作業後、以下を報告してください。

- 変更したファイル
- 追加・修正・削除したコメントの概要
- 処理内容を変更していないことの確認
- 関数名、クラス名、変数名を変更していないことの確認
- 文字コードを変更していないことの確認
- 要確認事項
````

# 作業内容

対象ソースコードと既存ドキュメントを確認し、現行仕様を整理してください。

特に以下を重視してください。

- 入力JSONから出力までの処理流れ
- CLI引数の扱い

## コメント記述ルール

STEP.1のコメント整理では、コメントの粒度と形式をある程度統一する。

主要クラス・主要関数には、必要に応じてDoxygen風のコメント形式を使用する。

- 解の更新に関係する処理
- 破壊法・修復法・近傍探索の中核処理
- JSON入力処理
- 副作用がある処理
- 前提条件が分かりにくい処理

自明なgetter/setterや短い単純処理には、冗長なコメントを付けない。
